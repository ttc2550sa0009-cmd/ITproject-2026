# TODOアプリ V1 要件定義書

## 1. 目的と背景

- 既存の Node.js + Express + TypeScript サイトに、PostgreSQL（Neon）を使った TODO アプリを追加する。
- 授業の第3回・第4回で、要件定義・設計・実装・テスト・公開までの一連の流れを、実際のコードと DB を使って確認する。
- 完成条件は、DB の CRUD、Fetch を用いる画面、ローカル / Vercel Preview / Production の3環境でのテスト、文書4件、SQL、Pull Request である。

## 2. 対象者

- この TODO アプリを使う人：授業で自分の TODO を管理する学生本人。
- V1 では認証を追加しない。ほかの人の TODO と区別する仕組みも V1 の対象外とする。
- 架空の授業用データだけを使う。氏名、メールアドレス、パスワードなどの個人情報は入力しない。

## 3. 実装環境

- サーバー：Node.js + Express + TypeScript（既存の `index.ts`）
- DB：PostgreSQL（Neon）
- DB 接続：`db.ts`（`pg` の Pool を使用）
- 公開：GitHub（`ITproject-2026`）→ Vercel（自動デプロイ）
- 既存のルートは残す：第2回までのトップページ `/` と接続確認 `/api/db-check` を残す。
  - 注意：現時点のプロジェクトには `db.ts` と `/api/db-check` がまだない。Neon 接続の実装とあわせて追加する（要確認：20261013 Neon の手順で作成済みの Neon データベースがあるかどうか）。

## 4. 画面と API の URL

- TODO 画面：`/todo`
- TODO API：`/api/v1/todos`
  - 要確認：ドキュメント内では、別の箇所に `/api/todo/v1/todos` と書かれている。REST の表と作業手順では `/api/v1/todos` になっているため、本書では `/api/v1/todos` を正とする。第6章の V1 共通仕様と照合して、食い違いがあれば修正する。

## 5. 機能要件

### REQ-01 TODO 一覧を取得する

- `GET /api/v1/todos` で、DB に保存された TODO を一覧で取得する。
- 画面 `/todo` を開くと、Fetch で一覧を取得して表示する。
- 並び順：作成日時の新しい順とする（要確認：第6章で別の指定がある場合はそちらを優先する）。
- 完了した TODO も一覧に含める。V1 では絞り込みはしない。
- 確認したら完了と言える状態：データ0件なら、GET の `data` が空配列になり、画面に「TODOがありません」と表示されること。

### REQ-02 TODO を登録する

- `POST /api/v1/todos` で、新しい TODO を登録する。
- 入力する項目：タイトル（必須）。
- 入力バリデーション：
  - タイトルが空、または空白だけの場合は登録しない。画面にエラーを表示し、API は入力エラーを返す。
  - タイトルの上限は 200 文字とする（要確認：第6章で別の指定がある場合はそちらを優先する）。
- 登録に成功したら、作成された TODO を返し、画面の一覧を更新する。
- 確認したら完了と言える状態：タイトルを入力して登録すると、一覧にその TODO が表示され、画面を再読み込みしても残っていること。

### REQ-03 完了状態を変える

- `PATCH /api/v1/todos/:id` で、指定した TODO の完了状態だけを部分更新する。
- 完了状態だけを更新するため、PUT ではなく PATCH を使う。
- リクエストには完了状態（`completed`）を含める。
- 存在しない ID を指定した場合は、未発見（404）を返す。
- 確認したら完了と言える状態：チェックを切り替えると、完了状態が変わり、画面を再読み込みしてもその状態が残っていること。

### REQ-04 TODO を削除する

- `DELETE /api/v1/todos/:id` で、指定した TODO を削除する。
- 存在しない ID を指定した場合は、未発見（404）を返す。
- 削除は繰り返しても最終状態が同じになる。
- 確認したら完了と言える状態：削除した TODO が一覧から消え、画面を再読み込みしても表示されないこと。

## 6. TODO の項目（V1）

| 項目 | 説明 |
| --- | --- |
| id | TODO を区別する番号。DB が自動で付ける。 |
| title | TODO のタイトル。必須。 |
| completed | 完了状態。はじめは未完了。 |
| created_at | 作成日時。DB が自動で記録する。 |
| updated_at | 更新日時。DB が自動で記録する。 |

- V1 では上記の項目だけとする。優先度は V2 で追加し、V1 では対象外とする。

## 7. 画面の動き

- `/todo` を開くと、一覧を取得して表示する。
- データが0件の場合は「TODOがありません」と表示する。
- 登録フォームでタイトルを入力して登録できる。空のまま登録しようとした場合は、画面にエラーを表示する。
- 各 TODO に完了状態を切り替える操作と、削除する操作を用意する。
- API がエラーを返した場合は、画面にエラーを表示し、一覧が壊れた状態にならないようにする。
- 画面は Fetch を使って API とやり取りする。画面の再読み込みなしで一覧が更新されること。

## 8. エラー時の扱い

- 入力エラー：タイトルが空の場合など。API は入力エラーのステータスと、画面に表示できるメッセージを返す。
- 未発見：存在しない ID を指定した場合。API は 404 を返す。
- DB 接続エラー：DB に接続できない場合。API はサーバーエラーを返し、接続文字列やパスワードなどの情報をレスポンスに含めない。
- 画面では、エラーが起きてもほかの TODO が表示できなくならないようにする。

## 9. 環境別の確認方法

- ローカル：`http://localhost:3000/todo` と `http://localhost:3000/api/db-check` を開く。`npm run dev` で起動する。
- Vercel Preview：Pull Request から作られる Preview 環境で、`/todo` と `/api/db-check` を開く。
- Production：Vercel の本番 URL で、`/todo` と `/api/db-check` を開く。
- `/api/db-check` は、DB に接続できている場合に `{"status":"ok","database":"connected"}` を返す。

## 10. 対象外の機能（V1）

- 認証（ログイン・ユーザー区別）
- 優先度の設定と表示
- 絞り込み・検索（クエリによる検索条件）
- 第2回の商品一覧演習（必須条件ではない）
- TODO 以外の機能追加

## 11. セキュリティと個人情報の配慮

- V1 では認証を追加しない。公開 URL を知っている人は TODO を見たり変更したりできる前提で、架空の授業用データだけを使う。
- 個人情報を入力しない。
- 接続文字列、パスワード、API キーは、要件定義書・設計書・実装手順書・コード・Git のいずれにも書かない。
- `.env` は Git の管理対象から除外する。Vercel の環境変数は Vercel 側で設定する。

- `db.ts` と `/api/db-check` は 20261013 Neon の手順で作成済みのはずだが、現時点のプロジェクトにはない。Neon の手順からやり直すか、今回の実装で追加するか。
- TODO 画面のファイル配置は `views/todo/` でよいか。ドキュメント内では `views/index.ejs` と書かれている箇所もある。
- タイトルの上限と一覧の並び順は、第6章で別の指定があるか。
